**Key Characteristics:**

- Compact controls inside spacious work areas.
- Persistent list selection and a contextual inspector.
- Semantic color paired with explicit status text.
- Light, dark, and system appearance with reduced-motion support.

## Colors

### Primary

The blue `accent` supports primary actions, links, selected navigation, and planning states. `accent-hover` deepens the light-theme action on hover; `accent-ink` supplies its contrasting text. `focus` is the explicit keyboard outline. Use the matching `dark-` tokens when dark appearance is active.

### Neutral

`bg` is the main workspace and field fill; `sidebar` separates navigation; `surface` supports quiet secondary areas; `hover` identifies interactive rows; `selected` preserves selection. `text`, `secondary`, and `line` provide graphite hierarchy and fine separation. The dark palette uses the same roles with brighter text and blue action fills.

Success and danger colors convey operational status. They supplement words and small symbols; the green Configured badge indicates saved model/key configuration, not verified access.

**The Truthful Color Rule.** Pair state color with an explicit label tied to the current workspace state.

## Typography

The native system sans stack is shared across navigation, controls, and body content. Page headings use the headline token; section titles use title. Interface copy is usually 12–13px, while secondary metadata and hints use 10–11px. Body paragraphs use a 1.6 line height. The prompt composer uses 17px text on desktop and 16px at small widths. Technical paths, IDs, and structured output use the code stack.

The extracted small-size roles are deliberate: caption is for short status labels and shortcut hints; detail is for supporting metadata, field hints, and compact actions; interface is for record names, input values, and navigation labels. Composer also supplies the brand wordmark size. Inspector-title also sizes large avatar initials. Headline-split applies while the inspector shares the workspace, and headline-compact applies at narrower widths. These roles record the current surface, not a recommendation to shrink primary reading text.

Keep heading weight and modest negative tracking; avoid turning application headings into marketing display type. Status counts use tabular numerals. Provider description copy is limited to 68ch.

## Layout

The desktop frame uses a fixed 224px sidebar, a sticky 56px toolbar, and a main content maximum width of 1160px. Standard main padding is 46px 48px 64px. Settings content caps at 760px. The inspector is 340px wide and preserves the list alongside it.

At 1150px and below, main padding tightens and the inspector narrows to 310px. At 950px and below, navigation becomes 200px and the inspector becomes a fixed overlay up to 360px. At 700px and below, navigation becomes a dismissible 224px drawer, workspace margins clear, and content uses 20px horizontal padding. Closed navigation is hidden from keyboard access; the open drawer traps focus and restores it when dismissed. At 1500px and above, content receives more top space and a taller composer.

Provider URL and model fields use a 1.35fr / 1fr grid with an 18px gap; the API key spans the form width. At 700px and below, fields and footer stack. Labels and hints remain with their controls, and the save button aligns to the start. Long paths and inspector text wrap; record titles truncate within flexible rows.

Proposal review uses one vertically ordered surface below the composer. Candidate agents, assumptions, validation, requirements, and the next question are separated by fine rules with 20px section spacing. At 700px and below, the proposal heading and state stack. Choice labels wrap with descriptions beneath; text answers use a vertically resizable field. Technical JSON sits behind disclosure and scrolls within a bounded area.

## Elevation & Depth

Most structure comes from surface tones and single-pixel dividers. Shadows belong to dialogs, toasts, and the overlaid inspector. The light floating shadow is `0 12px 40px #17253f1c`; dark floating surfaces use `0 12px 40px #0005`. Dialog backdrops use dialog-scrim with a 3px blur. The narrow navigation drawer uses the lighter navigation-scrim so the surrounding workspace remains visible. The narrow inspector shadow is `-8px 0 30px #17253f12`.

Controls transition color, background, and shadow over 140ms ease. The inspector enters over 180ms with `cubic-bezier(0.16, 1, 0.3, 1)` and a small horizontal translation. Reduced-motion mode disables animations and transitions. Motion clarifies state changes rather than delaying access.

## Shapes

Small edition badges and shortcut keys use badge; utility icon buttons and loading placeholders use utility; avatars, empty-state symbols, and toasts use avatar; the provider status panel uses provider-panel. Controls and navigation use the control radius; feedback uses the slightly softer feedback radius. The composer and proposal use the composer radius; floating dialogs use the dialog radius. Status dots are circles, while status labels remain unboxed text. Lists use straight dividers rather than individual elevated cards. Icons are compact line SVGs; the inspected surface requires no raster illustration.

## Components

- **Buttons:** solid blue for the main action, bordered workspace fill for secondary actions, and quiet icon/text controls for utility actions. Disabled controls reduce opacity to 0.5. Keyboard focus uses a 2px focus outline offset by 3px; pressed enabled buttons use brightness(0.96).
- **Navigation:** a soft selection fill, accent text, and stronger weight identify the current page. Counts and shortcuts stay secondary. The command dialog provides searchable destinations and keyboard navigation.
- **Work Requests:** Work offers Tasks and Requests views using the incumbent tab vocabulary. Requests defaults to Clarification requested and offers Awaiting acceptance, Accepted, Completion review, Completed, Failed, Rejected, Canceled, and All requests. It lists workspace-scoped requests in 20-row pages with one lookahead, polls every five seconds, and retains previously loaded rows with stale/error guidance on refresh failure. Capability gates distinguish listing from inspection; names come from the agent/team catalogs with ID fallback. Opening a row validates its parent-task identity, guards late responses after view changes/unmount, and binds the exact selected request to that source run even beyond its first request page. Show all requests for this task returns to the broader inspector list. Guide the lead reuses user-intervention semantics. Task-intent navigation from Home View all or successful agent-task creation selects Tasks explicitly; generic Work navigation retains the current view.
- **Work browsing:** search task descriptions and statuses across the scoped workspace before pagination, with case-insensitive literal matching and an explicit newest-first explanation. All work, In progress, Completed, Failed, Paused, and Canceled filters share the existing toolbar. Changing query or filter returns to the first page. Previous page and Next page expose 25 visible records with one lookahead to determine availability; range feedback receives focus after paging or retry. Different views show loading placeholders, while background refresh of the same view keeps existing rows visible. Canceled requests cannot replace a newer view. Empty states distinguish no matches, an empty later page, and no work; recoverable errors offer Try again. Unavailable browsing uses neutral workspace-capability copy. Offset pages are live and may shift as new tasks arrive; this is not a snapshot or a scalability guarantee.
- **Records and inspector:** full-width rows have fine separators, hover fill, and persistent selection fill. Selection focuses the inspector; closing it restores the originating row or page heading. Structured output wraps within the panel.
- **Draft recovery:** save prompt, composer mode, and assigned-agent ID together in one versioned draft record. Reopening restores the complete editing context without submitting work. Missing or malformed records fall back to the legacy prompt with agent-creation mode. A saved assignment that is loading or unavailable remains explicitly selected as such; the UI does not silently substitute another agent. Unavailable-agent guidance is linked to the selector, and both submit and keyboard submission require an active assignment for work. Choosing another active agent keeps the draft text and persists the new context.
- **Composer and proposals:** mode controls sit above a spacious textarea, with capability guidance and the submit action beneath. Proposal review shows readable candidate names, purposes, skills, expandable instructions and operating principles, assumptions, validation messages, and required capabilities. Raw candidate JSON is secondary, inside Technical details. The status distinguishes active generation, completed evaluation, input required, and failure; a generation error is shown for a failed proposal rather than carried forward as an active error after recovery. A saved apply receipt accurately distinguishes application with and without activation. Unapplied proposals explain whether installation actions are currently authorized, and rejected proposals remain explicitly uninstalled.
- **Refinement questions:** show the highest-priority unanswered question whose dependencies are satisfied. Use radio controls for a single choice or boolean, checkboxes for multiple choices and skill selections, and textareas for text or one-item-per-line lists. Cardinality guidance states the required count or range; invalid counts disable submission, duplicate list items are removed, and reaching a selection maximum disables additional unchecked options. Unsupported or credential-reference questions explain the limitation; they do not solicit a secret into a generic text field.
- **Proposal authority and recovery:** refine and retry depend on capabilities matching both the proposal ID and revision. Checking actions can recover from unavailable or failed capability discovery. Saves lock concurrent submission, include the expected revision, and reuse an idempotency key for an unchanged operation payload after an uncertain response. Conflict recovery fetches the latest proposal and asks the user to review it before retrying. An unchanged question and answer schema preserve the local draft across revision refresh; switching question/schema resets its controls. Delayed responses from another proposal or an older revision cannot replace the active proposal. Save and error feedback receive focus and describe the actual action.
- **Installation review:** a separated section summarizes proposed agents, any team, activation intent, maximum risk, and approval thresholds. Host policy runs through Check installation. The owner must explicitly check that resources, instructions, permissions, and activation behavior were reviewed before Approve installation becomes available. Approval and installation are separate actions. The final button says Install and activate or Install without activating according to the candidate; unknown intent prevents mutation. Matching proposal ID/revision capabilities, candidate digest, and eligible evaluation requirements guard the actions; reviewed consent resets when the revision or digest changes. Mutations retain idempotency keys for unchanged uncertain requests, block duplicate clicks, and refresh conflicts for review. The receipt shows Installed, states the resulting activation behavior, moves focus to the success heading after an in-session install, and offers View agents. Initial inactive installation and subsequent reviewed activation are supported; advanced placement/credential mapping remain incomplete.
- **Later activation:** an inactive receipt offers Review activation only when an exact-revision capability permits it. Preparation creates a deterministic child proposal over the same resources without requesting model generation; the original installation receipt remains immutable. The child ID is saved for reload recovery and its heading receives focus. Activation proposal copy identifies the inherited prompt as Original installation request and inherited assumptions as Original installation assumptions, with an explicit explanation that they describe installation history. Check activation, the explicit owner review checkbox, Approve activation, and Activate resources keep review, decision, and mutation distinct. Successful application shows Activated, focuses that heading, and retains View agents. Uncertain preparation retries use the same idempotency key for the same payload; capability, revision, digest, and parent checks prevent stale responses from changing the wrong proposal.
- **Work status and new attempts:** the inspector explains queued, planning, running, paused, scheduled sleep, dependency, agent, event, approval, failed, and canceled states using their actual causes. Provider-retry guidance appears only for a sleeping run whose wake reference is `hosted-turn-retry`, alongside a valid local scheduled date/time and Open provider settings. Budget admission text names the last check, required and remaining amounts, and dimension; exhausted capacity may be reserved rather than spent. Resume remains governed by capabilities and run state, never disabled solely because the budget says exhausted, and rechecks capacity. The app cannot raise the budget. Failed or canceled `agent_work` with create capability offers Review a new attempt: it copies the goal into Home, retains the assigned agent only if still active (otherwise requires selection), and focuses the composer after navigation. Separate submission creates a new run and leaves the original intact. A different unfinished draft requires an inline Replace draft and review / Keep draft decision; the replacement button is focused and linked to its explanation, while Keep draft preserves content and restores focus. Existing Start work navigation also defers composer focus until the next frame.
- **Collaboration inspector:** Delegation and requests lazily loads outgoing requests scoped to the run, starting expanded when the inspected run is waiting for another agent. Twenty rows plus a lookahead, three-second polling while open, manual refresh, inline stale-data/error feedback, and related-work links keep the context inspectable. Requests show state, kind, goal, sender/recipient names with ID tooltips, This team for the owning team, clarification, distinct response, completion/review summaries, resolution, and disagreement guidance. Identical question/response text appears once. Parent and delegated-work links validate returned identity and ignore callbacks after leaving. Guide the lead opens and focuses the existing guidance editor, prefilling request context only when no draft or pending request exists. It saves a user intervention with the existing persisted identity/revision protections; it neither impersonates an agent nor directly answers/approves the canonical request. The lead can subsequently clarify that existing request. Paused guidance waits for Resume. Guidance textareas use the shared bordered field styling and existing palette/radius; request prose preserves lines and wraps long text. Workspace-wide discovery is available in Work Requests; direct manual request management remains unfinished.
- **Task guidance:** Add guidance opens a capability-gated, labeled 4,000-character form inside Work controls and focuses its textarea. Help explains that paused work stays paused, sleeping work wakes, and existing approval/dependency waits remain; already-started actions may finish. Draft and pending request identity are saved locally before submission. An uncertain request locks the text read-only and offers Check saved guidance / explicit Retry guidance using the same UUID across reopening. A conflict refreshes current state and preserves the draft without automatically resending; definitive client errors say guidance was not saved. When the task ends or capability is unavailable, retained text remains read-only with a copy explanation. Success closes the form and focuses feedback. Saved guidance history identifies instructions, actor, and time while explicitly declining to claim the instruction was followed. The runtime rejects unapplied stale-turn proposals/output after guidance changes, including recovery, preserves usage, and continues within budget. Already-applied actions and partial artifact publication remain unaffected.
- **Work controls:** show Pause work for every supported nonterminal state other than paused, and Resume for paused work, gated by scoped capabilities. Cancel work opens an inline explanation that saved results remain and already-started external actions may finish. Confirm cancellation receives focus and references that explanation with `aria-describedby`; Go back restores focus to Cancel work. A revision change invalidates the pending confirmation and asks the user to review the new state. Commands lock concurrent submissions and carry the expected revision. Conflicts fetch the latest run without automatically replaying a command; uncertain responses instruct the user to inspect status before retrying. Feedback receives focus. Same-run identity and monotonic revision guards on commands and polling prevent delayed responses from switching or regressing the open inspector.
- **Channel settings and availability:** the channel list defaults to Active, with Archived and All filters; an explicit filter change clears selection. Successful settings changes retain the inspected channel and merge list title/revision monotonically. Update capability exposes rename and archive/restore controls; shared fields retain their existing palette/radii, title inputs stay single-line height, and narrow toolbars wrap. Rename drafts persist with their base title; remotely changed names require latest-state review before overwriting. Archive/restore explain posting consequences and require confirmation, invalidated by newer revisions; cancellation restores focus. Archive preserves messages and drafts while stopping new posts, restore re-enables posting, and neither cancels team tasks. Exact pending changes persist before PATCH; storage failure prevents sending. Uncertain/conflicting delivery requires Check saved channel via GET, never automatic replay. Recovery validates identity, owner, and monotonic revision and reports matching desired state without claiming who caused it; local recovery survives reload and unmounted responses are ignored.
- **Channel-to-work handoff:** Use as team work is available with create-team capability on readable channel messages, including archived channels. It opens a focused inline review in the existing Team work panel without starting a request. ## Do's and Don'ts

- Do preserve the selected row while showing its inspector.
- Do keep field labels, retention guidance, and recovery instructions adjacent to the relevant control.
- Do use real workspace capabilities and distinguish configured credentials from verified provider access.
- Do retain visible keyboard focus and restore focus when dismissing transient UI.
- Don't display a saved API key or put it back into an input.
- Don't label a refresh as a mutation retry.
- Don't imply proposal generation activated an agent.
- Don't treat this documentation or the bounded visual acceptance as comp approval or full product completion.
