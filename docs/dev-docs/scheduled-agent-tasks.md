# Scheduled agent tasks

Chat exposes scheduled work through the bundled `openseal.runbooks` Skill:

- `create_task` saves an active Objective and an Objective-owned routine activation with a self-contained goal, explicit six-field cron, IANA timezone, and optional occurrence limit.
- `list` pages through the current Agent or Team's routines and returns their exact IDs, revisions, schedules and reporting destination.
- `set_status` pauses, resumes or permanently retires future occurrences using a revision check. It does not cancel an execution already in progress; use Run controls for that.
- `set_script` makes a script routine run its chat file's current version (see below).
- `start` runs an existing activation on demand. `replace_schedule` creates a new generation after retirement, retaining work, authority, budget and reporting.

Scheduled tasks use the existing persisted activation cursor, replica-safe scheduler, deterministic occurrence Run IDs, concurrency admission and terminal reporting. The execution method is `task` rather than an immutable Runbook graph. Each occurrence is ordinary hosted Agent work, resolving the current deployment and its current tool bindings and approval requirements. Scheduling never copies credentials or confers future action authority.

The kernel derives the owner, tenant, assigned Agent, reporting conversation and originating user message from the durable chat Run. Creation requires a user message visible to that channel and cannot be invoked recursively from background work. Callers cannot choose a foreign tenant, Agent or reporting chat. Task results and failures appear in the original conversation; retries do not duplicate results. Archived or unavailable destinations and inactive deployments suspend execution.

The create and lifecycle operations retain normal write-risk policy and approval evaluation. Their action receipts confirm saved work; they do not assert future reads or writes succeeded. Exact action idempotency and lifecycle action receipts recover partially completed retries, while stale revisions from different calls remain conflicts.

Chat-authored tasks have an independent lifecycle from an Agent's embedded Runbook. Agent definition amendments and workforce projection replacement preserve those tasks. Persistence uses the existing tenant-filtered Objective, Runbook activation, Run and conversation stores; no new tables or schema migration are needed.

## Routines that run a saved script

Work that is the same steps with new data each time can run a saved script instead of re-planning with the model. The Agent writes and tests the script in the chat's sandbox with `workspace.run_command`, then proposes `create_task` (1.8.0) with `script: {path, command, timeoutSeconds?}`. The path is a normalized chat file path of plain characters; the command runs only that file (`python3 <path>`, `node <path>` or `bash <path>`, then plain arguments without quotes or shell characters); the timeout is at most 600 seconds (default 300).

When the proposal is made, the kernel reads the chat's files (`WithChatFileContent`, through `chatfs`) and writes `script.digest` (the file's content hash) and `script.filesVersion` (the immutable chat files snapshot holding it) into the arguments, discarding any model-supplied values. The approval preview carries `script: {path, digest, filesVersion, command, timeoutSeconds}`, which the brief card shows as its **Runs** line, and approval stores exactly that pin on `ScheduledAgentTask.Script`. Later edits to the file never change what the routine runs. `Engine.RoutineScriptStatus` reports `changed` (and `missing`) when the chat file's current digest differs from the pin; `set_script {activationId, expectedRevision}` re-pins to the current version and, like `create_task`, is always approved with a preview carrying `script`, `previousScript`, title, goal, schedule and grants. Keeping the approved version needs no call.

Approving a script's version (applying `create_task` or `set_script`) sets `script.approvedAt`; it is never proposed and is not part of the approved arguments. `RoutineScriptStatus.pinned` and `set_script`'s `previousScript` carry it, and a conversation's routine projection carries `script: {path}`.

An occurrence is an ordinary agent run in its chat: the model runs the script with `workspace.run_command`, as it would in the chat, then reports and may take more turns (for example granted posting actions). There is no separate execution path. Two kernel guards keep it to the approved script:

- **Pin.** Every Turn of the occurrence (whose Run context carries the pin it started with, `routineScript`) sets `HostedTurnRequest.commandPins [{path, digest, filesVersion, command, timeoutSeconds}]` and tells the model to run exactly the approved command first. The host attaches the pin to every `run_command` that invokes the file with `workspace.PinRunCommand`: the host-only argument `expectedDigest {path, digest, filesVersion}`, which is not in the model's input schema. A host honoring `expectedDigest` restores the file from snapshot `filesVersion` when the working copy differs, after checking its digest, and refuses to run otherwise (result `refused`); the result echoes `expectedDigest` when it ran. The host returns `pinnedCommands [{command, workingDirectory?, path, digest, exitCode, timedOut, refused, outputTail}]` (`workspace.RecordPinnedCommand`); the kernel validates them against the pins and keeps them in the kernel-owned checkpoint key `_opensealPinnedCommands`.
- **Completion check.** A Turn that would complete the Run without a record of the approved command, from the chat files root, at the pinned digest, exiting 0, does not complete it. The kernel records a final failure of kind `script` ("The routine's script did not run: …", "… exited with status N: …" with the last output lines, "… timed out after N seconds: …", or "… could not run: …"), and the model, with no actions or tools and the script failure instruction, explains it in place of its report. The Run fails with that explanation.

A bounded browser test can request: "Every minute in Asia/Kolkata, use the browser to fetch the current public forecast and post a sourced summary here. Run exactly twice, then stop." Verify two scheduled executions, two resulting messages, and retirement at the occurrence ceiling. Use a temporary conversation rather than altering an existing user's routine.
